Phase 1 Foundations weeks 1–2
Project scaffold
Create the repo, pyproject.toml, folder structure (cli/, core/, publishers/, config/, utils/), and get lpm --help running
structure
Config system
config.toml loader, .env token reader, pydantic schema validation, defaults. The single typed config object the rest of the app consumes
config
lpm init wizard
Interactive first-run setup — Gitea URL, usernames, token prompts, write config.toml and .env, create packages dir
cli
Local registry
registry.toml in ~/.lpm/packages tracking name → path → version for all known local packages
core
Phase 2 Core package management weeks 3–5
lpm new
Scaffold a new project — prompts for name, description, Python version, local deps. Writes pyproject.toml, README, .gitignore, tests/
cli
lpm add
Add a dependency — local packages by name (registry lookup → editable pip install) or PyPI packages. Supports --no-edit flag
core
Venv management
Auto-create .venv, detect system python vs python3, handle externally-managed-environment errors gracefully per distro
core
Lockfile (lpm.lock)
Write and read lpm.lock with full dep tree — source (local/gitea/pypi), path, version, editable flag, github_mirror if published
core
lpm install
Restore a project from lpm.lock — clone missing local deps from Gitea, create venv, install everything. The "someone else cloned it" command
cli
lpm list / status
Show installed deps with source and version. Status checks for updates on non-editable local packages
cli
Phase 3 Gitea integration weeks 6–7
Gitea API client
httpx-based client in publishers/gitea.py — create repo, push, check existence, handle auth via token from .env
publishers
lpm push
Commit changes, prompt for version bump (patch/minor/major), tag, push to Gitea. Update local registry with new version
cli
lpm package new
Register an existing project as a local package — create Gitea repo if needed, add to registry, write pyproject.toml if missing
cli
Git helpers
utils/git.py wrapping GitPython — init, add, commit, tag, set remote, push. Used by push and publish commands
utils
Phase 4 Publishing pipeline weeks 8–10
Dep tree analyser
Walk the full dependency tree recursively, classify each node (pypi/local/gitea), detect chains of local deps that need publishing first
core
lpm publish github
Publish deps to GitHub first (correct order), rewrite pyproject.toml with git URLs, push project, revert pyproject.toml to local form
publishers
lpm publish pypi
Build with python-build, upload with twine. Warn on local-only deps, offer to publish them to PyPI first or vendor them
publishers
Publisher base class
publishers/base.py abstract class — pre_publish, publish, post_publish hooks. Each target implements it so adding new targets is just a new file
publishers
Vendoring
Copy local dep source into _vendor/, rewrite imports. The fallback when a dep absolutely cannot be published anywhere public
publishers
Phase 5 Polish & release weeks 11–12
Test suite
pytest unit tests for resolver, config loader, venv logic. Integration tests for install/publish flow against a real or mocked Gitea
tests
Error handling
Friendly distro-aware errors (venv missing, python not found), consistent rich formatting, no raw tracebacks to the user
ux
Docs
getting-started.md, configuration.md, commands.md reference, architecture.md. README with install + quick-start
docs
CI / release
GitHub Actions — run tests on push/PR, publish lpm itself to PyPI on version tag. .github/workflows/ci.yml + release.yml
ci
